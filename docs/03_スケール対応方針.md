# 200拠点規模への対応方針

> **この文書の位置づけ**
> 実装は行っていない。いま現実に何が起きるのかと、どういう順序で手を入れるのかを、
> 判断の根拠ごと残しておくための文書である。
>
> スケールの話は「Redisを入れる」「キューにする」といった手段から書かれがちだが、
> それでは後から読んだ人に、なぜその手段なのかが伝わらない。
> ここでは **業務の形 → 負荷の形 → コードの具体的な箇所 → 対策** の順で書く。
>
> 数字はすべて仮説である。フェーズ0の計測で置き換える前提で読むこと。

---

## 1. 前提となる業務の形

**記録は送迎の「後」ではなく「前」に入力される。**

通所介護の一般的な運用では、送迎が終わってから記録を書く。
しかし CareLoop では、**送迎の前に入力する**ことを前提に設計している。
ご家族へお渡しする連絡帳を、送迎車が出る前に仕上げる必要があるためである。

これは制約ではなく、このアプリの狙いそのものである。

- 記録を前倒しすることで、**連絡帳を送迎時に手渡しできる**（F-16 日次の連絡帳）
- 生活相談員の手が空くのを待たず、**介護職員が自分の見た内容で記録を起こせる**
- 音声入力とAIの三面変換（F-LLM-05）は、この前倒しを現実的にするための機能である

したがって **負荷の山は「送迎の直前」に立つ**。
事業所ごとに送迎の出発時刻は異なるが、多くは午後の同じ時間帯に集中する。
一般的な運用から推すと **14:30〜16:00 あたり**が山になる見込みだが、
これは仮説であり、フェーズ0で実測して確定する。

> 当初、山を「送迎後の16〜18時」と見込んでいたが、これは誤りだった。
> 業務の形を取り違えると、対策の当て先ごと外れる。ここを最初に書いておく。

## 2. 想定される負荷

### 2.1 規模

| 項目                      | 値                  | 根拠                                     |
| ------------------------- | ------------------- | ---------------------------------------- |
| 拠点数                    | 200                 | 前提                                     |
| 1拠点あたりの職員数       | 7〜10人/日          | 実運用の実績値                           |
| 1職員が記録するご利用者数 | 5人程度             | 実運用の実績値                           |
| **1日のログイン職員数**   | **1,400〜2,000人**  | 200 × 7〜10                              |
| **1日の記録件数**         | **7,000〜10,000件** | 1,400〜2,000 × 5                         |
| **1日のLLM実行回数**      | **7,000〜10,000回** | 記録1件につき三面変換1回。再生成分は別途 |

### 2.2 ピーク時の同時実行

記録の大半が **90分の窓**に入ると仮定する。

```
10,000件 ÷ 90分 ≒ 111件/分 ≒ 1.9件/秒
```

LLMの三面変換は**同期実行**で 6〜11秒（実測レンジ、平均8秒とする）かかる。
その間、PHP-FPM のワーカーは1本まるごと塞がる。

```
1.9件/秒 × 8秒 = 約15本のワーカーが、常時LLMの応答待ちで埋まる
```

送迎の出発時刻がさらに揃って **30分の窓**に圧縮された場合：

```
10,000件 ÷ 30分 ≒ 5.6件/秒 × 8秒 = 約44本
```

**これが最大の律速要因である。** 44本のワーカーが「何もせず待っている」ために
確保されている状態で、通常の画面表示のリクエストが後ろに並ぶ。

一方で、**同時にログインしている職員数そのものは大きくない**（ピーク時でも2,000人規模、
処理中のリクエストは数十本）。セッション数やDB接続数が先に破綻する形ではない。
対策の重心は **「LLM待ちでワーカーを塞がないこと」** に置く。

**確定させたいこと**：ピークの時刻・幅、その窓に入る記録の割合、LLM実行のp95レイテンシ。

## 4. フェーズ1：いま分かっている具体的な問題

計測を待たずとも、コードを読めば分かる問題がある。

### ① `whereDate()` が `service_date` の索引を使えない

**該当箇所**

| ファイル                                           | 行      |
| -------------------------------------------------- | ------- |
| `app/Http/Controllers/DashboardController.php`     | 67, 94  |
| `app/Http/Controllers/ServiceRecordController.php` | 59, 113 |

`whereDate('service_date', $date)` は SQL 上で `DATE(service_date) = ?` になる。
列に関数をかけるため、`service_records` に張ってある `index('service_date')` が使われず
全件走査になる。`service_date` は `date` 型で時刻を持たないため、
**関数をかける必要がそもそもない**。

```php
// 変更前
->whereDate('service_date', $date)

// 変更後
->where('service_date', $date)
```

日次1万件 × 保存期間を考えると、テーブルは年間300万件規模になる。
そこを毎回走査することになる。

### ② `service_records` に `facility_id` がなく、事業所の絞り込みが毎回サブクエリになる

`service_records` は `resident_id` しか持たない。
事業所で絞るには `residents` を経由するしかなく、`whereHas()` が相関サブクエリになる。
記録一覧・ダッシュボードのほぼ全てのクエリがこれを通る。

**対策**：`service_records.facility_id` を非正規化し、
`(facility_id, service_date)` の複合索引を張る。

正規化を崩すことになるが、**ご利用者の所属事業所は記録作成後に変わらない**ため、
整合性が壊れる経路がない。書き込み時に `resident->facility_id` を写すだけで済む。

### ③ 月次コストの合計を、ダッシュボードを開くたびに計算している

`app/Models/LlmRequest.php:95` の `monthlySpendUsd()` は
`whereBetween('created_at', …)->sum('estimated_cost_usd')` を実行する。

`llm_requests` の索引は `(feature, created_at)` と `(status, created_at)` の2本で、
**`created_at` 単体で始まる索引がない**。複合索引の第2列からは引けないため、
この SUM は索引を使えない。

年間300万件規模のテーブルに対して、ダッシュボードを開くたびに月初からの全行を合計する。

**対策**：`created_at` 単体の索引を追加する。
それでも重ければ、日次集計テーブルに落とすか、短いTTLでキャッシュする。
ただし**予算上限の判定にも使っている値**なので、キャッシュのTTLは
上限を突破しても気づけない長さにしてはいけない。

## 5. フェーズ2：保存の失敗

ピーク時に集中するのは読み取りだけではない。

### ④ 楽観ロックがなく、後勝ちで上書きされる

`ServiceRecordController::update()` は `DB::transaction()` の中で更新するが、
**「自分が読んだ後に誰かが変えていないか」を確かめていない**。

介護職員が記録を入力し、生活相談員が同じ記録を開いて確定する――という運用があるため、
同じ記録を2人が同時に開く場面は普通に起きる。
いま起きるのは例外ではなく、**片方の入力が黙って消える**ことである。
消えたことに誰も気づけない点が、記録として一番まずい。

**対策**：`updated_at`（またはバージョン列）をフォームに埋め、
保存時に一致しなければ「他の職員が更新しました」と表示して差分を見せる。

### ⑤ `unique(resident_id, service_date)` の競合が500になる

同じご利用者・同じ日の記録は1件という制約を張っている（正しい制約である）。
しかし2人が同時に新規作成すると、後から来た方は**制約違反の例外がそのまま500になる**。

**対策**：`updateOrCreate` に寄せる、または `QueryException` を捕まえて
既存レコードの編集画面へ誘導する。

### ⑥ LLM呼び出しはトランザクションの外に置き続ける

現状、LLM呼び出しはトランザクションの外にある。**この方針を変えない。**
6〜11秒かかる外部API呼び出しをトランザクションで囲むと、
その間ずっと行ロックを握り続け、接続プールを食い潰す。

非同期化（フェーズ3）でこの構造を崩さないよう、ここに明記しておく。

## 6. フェーズ3：LLM実行の非同期化（最も効く）

2.2節で見たとおり、**ピーク時に最大44本のワーカーがLLMの応答待ちで塞がる**。
これが最大の律速要因である。

要件定義 7.5節（F-LLM-06 LLM実行ジョブ管理）で設計済みだが、**未実装**である。
現状 `app/Jobs/` は存在せず、`LlmActionController` が同期で呼んでいる。

```
[Controller] llm_jobs に queued で登録 → job_id を即返す
     ↓
[Queue Worker] 実行（running）
     ↓
[完了] succeeded / failed、結果を保存
     ↓
[画面] job_id をポーリングして進捗表示
```

**これにより変わること**

- Webワーカーは記録の保存だけを担い、1リクエスト100ms以下で返す
- LLMの遅さはワーカー数と切り離され、**キューの長さとして現れる**
- キューが伸びればワーカーを足せばよい。Webの応答時間には出ない
- 失敗の再実行が仕組みとして成立する（現状は画面を開き直すしかない）

**注意点**

- 送迎前に連絡帳を仕上げる運用なので、**待ち時間の上限が業務上シビア**である。
  キューが伸びて5分待ちになると、送迎に間に合わなくなる。
  キューの滞留時間を監視し、閾値を超えたら管理者に見えるようにする
- 現状 `QUEUE_CONNECTION=database`。ピーク時のポーリングがDBを叩くため、
  非同期化と同時に Redis へ移す（フェーズ4）

## 7. フェーズ4：インフラ

順序として**最後**に置く。①〜⑥を残したままサーバーを増やしても、
同じ問題を人数分抱えるだけになる。

- **Redis**：セッション・キャッシュ・キューを移す。
  現状すべて `database` ドライバで、ピーク時にDBへ集中する
- **リードレプリカ**：ダッシュボードと一覧は参照のみ。書き込みと分離する
- **マルチテナンシーは単一DBのまま**：200拠点でDBを分けると、
  横断した集計（AI利用ログ・コスト監視）が成り立たなくなる。
  `facility_id` による絞り込みで足りる規模である
- **PHP-FPM のワーカー数**：非同期化(フェーズ3)の後に決める。
  先に増やすと、LLM待ちで塞がるワーカーを増やすだけになる

## 8. フェーズ5：データ量

| テーブル          | 年間の増加量（概算） | 方針                                                             |
| ----------------- | -------------------- | ---------------------------------------------------------------- |
| `service_records` | 約300万件            | 法定保存期間（完結の日から5年）は保持。索引はフェーズ1で対応     |
| `llm_requests`    | 約300万件            | 月単位でパーティション、または古い分を集計表に落として本体を削除 |
| `audit_logs`      | 記録の更新回数に比例 | 同上。`changes` を暗号化して持つため1行が重い                    |

`audit_logs` は変更前後の値を暗号化して保持する。
行数だけでなく**1行のサイズが大きい**ため、他のテーブルより早く効いてくる。

**法定保存期間を過ぎた記録の物理削除バッチ**（要件定義8章）は未実装である。
これを実装しないと、テーブルは増え続ける一方になる。

## 9. 着手する順序

| 順  | 内容                          | 理由                                         |
| --- | ----------------------------- | -------------------------------------------- |
| 1   | フェーズ0 計測                | 数字がないと、効かない場所を直すことになる   |
| 2   | ① `whereDate` の修正          | 4行の書き換えで済む。効果に対して手間が最小  |
| 3   | ③ `created_at` 索引の追加     | マイグレーション1本                          |
| 4   | ② `facility_id` の非正規化    | マイグレーション＋書き込み箇所の修正         |
| 5   | ⑤ 一意制約の競合を500にしない | ユーザーに見えている不具合                   |
| 6   | **フェーズ3 非同期化**        | 最も効く。同時に最も重い                     |
| 7   | ④ 楽観ロック                  | 非同期化で編集の同時性が上がるため、その後に |
| 8   | フェーズ4 インフラ            | 上が済んでから                               |
| 9   | フェーズ5 データ量            | 運用開始後、増加ペースを見て                 |

2〜5 は小さい変更でありながら、全ユーザーの全画面に効く。
6 は設計済み（要件定義7.5節）で、実装だけが残っている。
