## 1. 背景と課題

### 1.1 プロダクトの動機

作成者は介護施設運営企業（通所介護・福祉用具）において、開設準備・事業推進・営業企画・IoTプラットフォーム部門に約9年間在籍し、送迎ルート設定システムや勤務シフト作成システムの導入において、現場とベンダーの橋渡し役として要件整理・社内推進を担当した。

その過程で繰り返し observed した課題が、本プロダクトの出発点である。

### 1.2 現場の課題（As-Is）

#### 課題1：記録は「書く」が「読まれない」

通所介護では介護保険法により**サービス提供記録の作成と保存が義務**づけられている。現場では毎日、利用者1人あたり複数の記録（バイタル・食事・水分・入浴・排泄・機能訓練・その日の様子）が発生する。

しかし記録の多くは**「書いて終わり」**になる。1人の利用者について1ヶ月分の記録を通読しなければ気づけない変化（少しずつ食事量が減っている、水分摂取が続けて少ない、ふらつきの記述が増えている）は、日々の業務に追われる中で見落とされやすい。

#### 課題2：モニタリング（計画の振り返り）が属人的で重い

通所介護計画書には長期目標・短期目標が設定され、定期的にモニタリング（達成度の振り返り）を行う必要がある。しかし現場では、**過去1〜3ヶ月分の記録を人手で読み返して要約する**作業が発生し、担当者の記憶と主観に依存しやすい。結果として「特変なし」が並ぶ形骸化したモニタリング記録になりやすい。

#### 課題3：シフト交代時の申し送りに情報が落ちる

送迎担当、入浴担当、機能訓練担当と業務が分かれており、口頭とメモ中心の申し送りでは情報が欠落する。

#### 課題4：家族への報告が「業務の後回し」になる

家族は「今日どう過ごしたか」を知りたい。しかし職員にとって報告文の作成は最も後回しになりやすい業務であり、結果として「お変わりありませんでした」という定型文になりがちで、家族の満足度・信頼につながらない。

### 1.3 課題の構造

これら4つの課題は、いずれも **「大量の非構造テキスト（自由記述の記録）から、意味を取り出して人に届ける」** という同一の構造を持つ。これは従来のCRUD型業務システムでは解決できず、**LLMの適用が本質的に有効な領域**である。

これが、本プロダクトでLLM連携を中核に据える理由である。

## 2. プロダクト概要

### 2.1 コンセプト

> **話した一言が、記録にも、ご家族へのお便りにも、申し送りにもなる。**

介護職員はスマートフォンに話しかけるだけでよい。その1つの入力から、LLMが**文体の異なる3つの出力**を作り分ける。

```
 職員が音声で入力（1回）
        │
        ├─→ ① 記録用テキスト   … 法定文書としての文体。専門用語で正確に
        ├─→ ② 家族向けテキスト … 敬語・平易な表現。安心して読める文章に
        └─→ ③ 申し送り用メモ   … 簡潔。次の担当者が取るべき行動を明示
```

同じ出来事でも、**読む相手によって適切な書き方は違う**。その書き分けを職員が3回書いて実現するのは現実的ではなく、しかし省略すれば記録は形骸化し、家族への報告は定型文になる。ここがLLMの価値が最も明確に出る地点である。

蓄積された記録は、さらに「ケア計画の進捗要約」「リスク兆候の抽出」「月次の家族向け報告」へと集約される。**記録 → AI変換 → 現場・家族 → 次のケア** という循環（Loop）を回すことがプロダクト名の由来である。

### 2.2 提供価値

| 対象 | 提供価値 |
|---|---|
| 介護職員 | 記録の入力負荷を増やさずに、申し送りと家族報告の作成時間を削減 |
| 管理者・生活相談員 | 見落としやすいリスク兆候の早期発見。モニタリング作成の下書き自動化 |
| 利用者ご家族 | 「今日どう過ごしたか」が具体的に伝わる報告を受け取れる |

### 2.3 設計上の基本思想：Human-in-the-Loop

本システムは **LLMの出力をそのまま確定情報として扱わない**。

介護記録は利用者の健康と生命に関わり、また法定保存文書でもある。したがって、LLMの出力は必ず**「下書き」または「気づきの提示」**として扱い、以下を設計原則とする。

1. **LLM出力は必ず人が確認・編集してから確定する**（生成物をそのまま保存・送信しない）
2. **LLMの主張には必ず根拠となる記録ID・日付・該当箇所を添付させる**（ハルシネーション検証を可能にする）
3. **診断・医療判断は行わせない**（「〜の疑いがある」ではなく「〜の記述が増えている」という事実の提示に留める）
4. **家族向け報告は管理者承認を経て確定する**（二段階チェック）

この方針は制約ではなく、**業務システムにAIを組み込む際の要件そのもの**であり、本プロダクトの設計上の主張である。

## 3. スコープ

### 3.1 対象サービス種別

**通所介護（デイサービス）** — 定員20名程度の単独型事業所を想定。

選定理由：1日単位でサービスが完結するため記録の粒度が扱いやすく、バイタル・食事・入浴・機能訓練・レクリエーションと記録項目が多様で、LLMによる要約の価値が出やすい。

### 3.2 本システムで実現すること（In Scope）

- 利用者情報・通所介護計画書の管理
- 日々のサービス提供記録の入力（タブレット前提）
- ヒヤリハット・事故報告の記録
- **LLMによる目標進捗要約 / リスク兆候抽出 / 申し送り生成 / 家族向け報告下書き / 記録文の清書**
- 家族向け報告の承認フローとPDF出力
- 権限に基づくアクセス制御

### 3.3 本システムで実現しないこと（Out of Scope）

明確に線を引く。ポートフォリオとしての完成度を、スコープの広さではなく**設計の深さ**で示す方針のため。

| 対象外 | 理由 |
|---|---|
| 介護報酬請求（国保連へのCSV伝送） | 制度仕様が膨大で、本システムの主題（AI活用）と無関係 |
| LIFE（科学的介護情報システム）へのデータ提出 | 同上。ただしデータ構造は将来対応可能な形で設計する |
| 送迎ルート最適化 | 別問題領域 |
| 勤務シフト作成 | 別問題領域 |
| 家族向けWebポータル（家族ログイン） | 認証・権限の実装量が増えるため、初版はPDF出力で代替 |
| モバイルネイティブアプリ（App Store配信） | レスポンシブWebで対応する。iPhone は Safari で利用し、ホーム画面に追加して使う想定 |
| 音声データのサーバー保存・自社での文字起こし | 7.8節に記載のとおり、要配慮個人情報である音声を自社サーバー・外部APIに送信しない方針のため |
| オフライン対応 | 事業所内Wi-Fi・モバイル回線前提 |

### 3.4 前提条件・制約

- 実在の個人情報は一切使用しない。デモデータはすべて架空の利用者とする
- 本システムは学習・ポートフォリオ目的であり、実運用での使用は想定しない（READMEに明記する）
- LLM APIの利用料が発生するため、コスト上限制御を必須機能とする

## 5. 業務フロー

### 5.1 As-To（現状）

```
[送迎・来所]
   ↓
[バイタル測定] → 紙のバイタル表に記入
   ↓
[入浴・食事・機能訓練・レク] → その都度メモ、夕方にまとめて記録用紙へ転記
   ↓
[申し送り] → 口頭＋ホワイトボード（情報が落ちる）
   ↓
[連絡帳] → 手書きで数行（時間がなく定型文になりがち）
   ↓
[月次モニタリング] → 1〜3ヶ月分の記録を人手で読み返して要約（属人的・重い）
```

### 5.2 To-Be（本システム導入後）

```
[送迎・来所]
   ↓
[バイタル測定] → タブレットでその場入力
   ↓
[入浴・食事・機能訓練・レク] → 発生時点でタブレット入力（自由記述欄あり）
   ↓                              ↓
   │                        [F-LLM-05] 走り書きを記録文に清書（任意）
   ↓
[申し送り] → [F-LLM-03] 当日の全記録から申し送り案を自動生成 → 職員が確認・加筆
   ↓
[家族報告] → [F-LLM-04] 下書き3案を生成 → 職員が選択・編集 → 管理者が承認 → PDF出力
   ↓
[月次モニタリング] → [F-LLM-01] 目標ごとの進捗要約を自動生成（根拠記録付き）
                    [F-LLM-02] リスク兆候を抽出し重要度を判定（根拠記録付き）
                     → 管理者が確認し、対応を記録
```

**変化のポイント**：記録の入力負荷は変えず（むしろ転記が消える分減る）、記録の**出口**を増やしている。

### 6.2 主要機能の詳細

#### F-05 通所介護計画書管理

- 1人の利用者に対し、期間（開始日〜終了日）を持つ計画書を複数保持できる
- 1つの計画書は**長期目標1件**と**短期目標を複数件**持つ
- 短期目標は F-LLM-01 の評価単位となるため、独立したレコードとして管理する

#### F-07 サービス提供記録 入力

- 1利用者 × 1サービス提供日 につき1レコード（ユニーク制約）
- 自由記述欄「その日の様子」が **LLMへの主要な入力ソース**となるため、入力しやすさを最優先とする
- **音声入力を第一の入力手段とする**（技術方式は7.8節）。入力された生テキストは加工せずそのまま保存し、整形結果とは別カラムで保持する
- よく使う表現のクイック挿入ボタンを併設する（音声が使えない場面のため）

#### F-16 日次の連絡帳（お渡し用）

**通所介護の連絡帳は、本来「毎回」お渡しするものである。**

当初の設計では、ご家族向けの報告を月次のみとしていた。これは現場の実態に合わない。
月次のまとめだけでは、ご家族はその日の様子を知る手段がなく、体調の変化に気づいても
翌月まで共有されないことになる。ご利用の継続にも関わる。

日々のご家族向け文章は F-LLM-05（音声入力の三面変換）がすでに毎回生成している。
欠けていたのは、それをお渡しできる形にする出口だった。

**記載する内容**

| 項目 | 備考 |
|---|---|
| 本日のご様子 | F-LLM-05 が生成した `family_text` |
| お迎えの際にお伝えすること | 口頭連絡タスク（F-20）が未完了のもの |
| ご到着・お帰り時刻 | |
| 体温・血圧・脈拍 | 未測定は「未測定」と表示。0 で埋めない |
| お食事・水分 | 摂取割合は「8割ほど」等の平易な表現へ変換 |
| ご家族からの連絡欄 | 記入用の空欄。連絡帳は往復するもの |

**承認フローを月次と分ける（設計判断）**

月次報告は管理者の承認を経てから出力する。一方、日次の連絡帳は
**職員が記録を確認して確定した時点（`confirmed_at`）で出力できる**ようにする。

ご利用者20名分の連絡帳に毎日管理者承認を挟むと、送迎に間に合わない。
**現場が回らない統制は、結局は運用されなくなる。** 統制の強度は、
文書の性質と頻度に合わせて変える。

**AIが動かなくても出力できる**

ご様子の文章が未生成でも、バイタルと食事・水分は印刷できる。
その場合は「本日のご様子は、担当職員より口頭でお伝えいたします」と表示する。
LLMの障害でご家族への連絡が止まってはならない（8章 可用性）。

**出力方式：印刷用HTMLビュー**

PDF生成ライブラリを使わず、印刷に最適化したHTMLを返す。理由は2つある。

1. 現場は**紙で渡す**。ブラウザの印刷機能でそのまま紙にできる
2. ブラウザの「PDFに保存」でPDFにもなるため、PDF化の要件も満たせる

日本語PDFライブラリのフォント埋め込みは、環境差による文字化けを起こしやすい。
紙に出すという要件に対して、PDF生成は手段のひとつに過ぎない。

#### F-18 スマートフォン向け記録画面

介護職員は日中ずっと現場を移動しており、事務所のPCやタブレットの前に座る時間がない。**記録はその場で、片手で、数十秒で終わる**必要がある。

| 現場の制約 | 画面設計での対応 |
|---|---|
| 片手しか空いていない（もう片方で利用者を支えている） | 主要操作をすべて画面下部3分の1に配置。上部は情報表示のみ |
| 手袋・手が濡れている | タップ領域は最小 44×44px。隣接要素との間隔を8px以上確保 |
| 立ったまま・移動中 | 1つの記録を1画面で完結させ、画面遷移を挟まない |
| 書く時間がない | 音声入力を起点にし、AIが記録用の文体へ整形する |
| 屋外（送迎中）の明るい場所 | 本文と背景のコントラスト比 4.5:1 以上 |

対象端末は iPhone（Safari）。ホーム画面に追加してフルスクリーンで利用する想定とする。

#### F-17 デモデータ投入

ポートフォリオとして**クローンして即座に動かせること**を重視する。
- 架空の利用者20名（要介護度・年齢・疾患傾向を分散させる）
- 3ヶ月分のサービス提供記録
- うち3名には**意図的にリスク兆候を埋め込む**（体重減少、水分摂取低下、ふらつき記述の増加）

意図：レビュアー（採用担当者）が `php artisan migrate --seed` 後すぐに、LLM機能が意味のある出力を返す状態を体験できるようにする。

## 7. LLM連携機能 詳細設計 ★本システムの中核

### 7.1 アーキテクチャ方針

```
┌──────────────────────────────────────────────────────────┐
│ Presentation (React / Inertia)                            │
│   実行ボタン → ジョブ登録 → ポーリングで進捗表示 → 結果表示  │

│  └───────────────────────────────────────────────────────┘ │
└────────────────────────────────────────────────────────────┘
```

**設計上の主張**

1. **`LlmClient` をインターフェースで抽象化する**
   アプリケーション層はSDKの具象クラスに依存しない。テスト時とAPIキー未設定時は `FakeClient` に差し替え、**APIキーなしでもアプリ全体が動作する**。ポートフォリオとして「レビュアーがAPIキーを用意しなくてもデモできる」実用上の利点もある。

2. **ルールベース計算とLLMの役割を明確に分離する**
   数値で判定できるもの（体重減少率、水分摂取量、バイタル異常値）は**決定的なロジックで計算する**。LLMは「数値に現れない、自由記述の中の兆候」の抽出に用途を限定する。

   理由：LLMに算術を任せると再現性が失われ、検証もできない。逆にルールでは拾えない「最近ふらつきの記述が増えている」「レクへの参加意欲の低下」といった質的変化はLLMが得意とする。**適材適所の判断こそが設計であり**、これは「LLMに全部投げる」実装との決定的な差になる。

3. **すべてのLLM呼び出しは非同期ジョブとして実行する**
   LLMの応答には数秒〜数十秒かかる。HTTPリクエスト内で同期実行するとタイムアウトとUXの両面で破綻する。

### 7.2 個人情報保護（マスキング設計）

介護記録は個人情報保護法における**要配慮個人情報**（健康状態・病歴を含む）に該当する。外部APIへ送信する前に、以下のマスキングを必須とする。

| 項目 | 処理 | 送信例 |
|---|---|---|
| 利用者氏名 | プレースホルダ置換 | `{{RESIDENT_1}}` |
| 職員氏名 | プレースホルダ置換 | `{{STAFF_1}}` |
| 家族氏名 | プレースホルダ置換 | `{{FAMILY_1}}` |
| 事業所名 | プレースホルダ置換 | `{{FACILITY}}` |
| 生年月日 | 年齢に変換して送信 | `85歳` |
| 住所・電話番号 | **送信しない**（プロンプトに含めない） | — |
| 被保険者番号 | **送信しない**（DBでは暗号化保存） | — |

- 応答に含まれるプレースホルダは `PiiUnmasker` で画面表示時に実名へ復元する
- **監査ログ（`llm_requests`）にはマスキング後のペイロードのみを保存する**
- マスキング対応表はリクエストのライフサイクル内のみメモリ保持し、永続化しない

**この設計を要件に含める理由**：外部LLMサービスを業務システムに組み込む際、法務・情報システム部門から必ず問われるのが「その個人情報はどこへ行くのか」である。この問いに設計で答えられることが、業務システム開発者としてのAI活用スキルの本質だと考える。

### 7.3 各機能の入出力仕様

すべてのLLM機能は **JSONスキーマを定義し、構造化出力として受け取る**。

#### F-LLM-01 目標進捗要約

**入力コンテキスト**
- 通所介護計画書の長期目標・短期目標（複数）
- 指定期間内のサービス提供記録（自由記述「その日の様子」）
- 指定期間内の機能訓練記録、食事・水分摂取記録、バイタル記録の統計値

**出力JSONスキーマ**

```json
{
  "period": { "from": "2026-08-01", "to": "2026-08-31" },
  "overall_summary": "期間全体の総括（200字以内）",
  "goals": [
    {
      "goal_id": 12,
      "progress_status": "improving | unchanged | declining | insufficient_data",
      "comment": "この目標に対する評価コメント（150字以内）",
      "evidence": [
        { "record_id": 3412, "date": "2026-08-14", "excerpt": "根拠となる記録の該当箇所" }
      ]
    }
  ],
  "next_actions": ["次期に向けた提案（最大3件）"],
  "confidence": "high | medium | low"
}
```

**設計上のポイント**
- `evidence` を**必須項目**とし、根拠のない主張を構造的に禁止する。UIでは根拠記録へのリンクを表示し、職員が原典を即座に確認できるようにする
- `insufficient_data` を選択肢に含める。記録が不足している場合に無理に評価させず、「判断できない」と言わせることがハルシネーション対策になる
- `confidence` により、低確信度の出力をUI上で明示的に警告表示する

#### F-LLM-02 リスク兆候の抽出・重要度判定

**Step 1：ルールベース指標の算出（決定的ロジック / LLM不使用）**

| 指標 | 判定条件 | 検出リスク |
|---|---|---|
| 体重減少率 | `(前月体重 − 当月体重) ÷ 前月体重 ≥ 3%` | 低栄養 |
| 水分摂取量 | 1日総摂取量 1,000ml 未満が3日以上連続 | 脱水 |
| 食事摂取率 | 主食または副菜の摂取率が5割未満の日が週3日以上 | 低栄養 |
| 体温 | 37.5℃以上 | 感染症 |
| 収縮期血圧 | 180以上 または 90以下 | 循環器 |
| SpO2 | 93%以下 | 呼吸器 |
| 転倒・ヒヤリハット | 直近3ヶ月で2件以上 | 転倒 |

**Step 2：LLMによる質的兆候の抽出**

Step 1 の算出結果と、期間内の自由記述をLLMに渡し、**数値に現れない兆候**を抽出させる。

**出力JSONスキーマ**

```json
{
  "assessed_at": "2026-09-11T10:00:00+09:00",
  "risks": [
    {
      "category": "fall | aspiration | dehydration | malnutrition | pressure_ulcer | infection | medication | skin | bpsd | other",
      "severity": "high | medium | low",
      "title": "リスクの要約（30字以内）",
      "reason": "そう判断した理由（150字以内）",
      "source": "rule_based | llm_detected | both",
      "evidence": [
        { "record_id": 3455, "date": "2026-09-02", "excerpt": "歩行時にふらつきが見られた" }
      ],
      "suggested_actions": ["現場での確認事項（最大3件）"]
    }
  ],
  "no_risk_detected": false
}
```

**設計上のポイント**
- `source` により、その指摘が**ルールベース由来かLLM由来か**を区別して表示する。ルールベース由来は再現性があり信頼度が高い、LLM由来は要確認、という扱いの差をUIで表現する
- `suggested_actions` は「現場での**確認**事項」と定義し、**医療的な判断や指示を生成させない**。例：「受診を検討」ではなく「ご家族に最近の自宅での食事量を確認」

#### F-LLM-03 申し送り生成

当日の全記録から、次シフト担当者向けの申し送り文を生成する。

```json
{
  "service_date": "2026-09-11",
  "handovers": [
    {
      "resident_id": 7,
      "priority": "high | normal",
      "summary": "申し送り内容（100字以内）",
      "requires_attention": true
    }
  ],
  "facility_notes": ["事業所全体への連絡事項"]
}
```

#### F-LLM-04 家族向け報告 下書き生成

**要件**：LLMに完成品を書かせるのではなく、**トーンの異なる3案を提示し、職員が選んで加筆する**。

```json
{
  "drafts": [
    {
      "tone": "standard | warm | concise",
      "title": "9月の様子について",
      "body": "報告本文（400字程度）",
      "highlights": ["この案が強調している点"]
    }
  ],
  "cautions": ["記載を避けた事項（例：体調不良は電話でお伝えすべき内容のため本文に含めていない）"]
}
```

**設計上のポイント**
- `cautions` により、**LLMが意図的に書かなかったこと**を職員に伝える。家族への文書に含めるべきでない情報（重大な体調変化、他の利用者に関する情報）を機械的に除外し、その旨を明示する
- 3案から選択する形式は、白紙から書くより心理的負担が軽く、かつ「LLMの言いなり」にもならない中間解である

**承認フロー**

```
[職員] 下書き生成 → 案を選択 → 編集 → 承認依頼
                                        ↓
[管理者] 内容確認 → 差し戻し / 承認
                          ↓
                     PDF出力 → 印刷してご家族へ手渡し
```

ステータス遷移：`draft → pending → approved`（差し戻し時は `pending → draft`）

#### F-LLM-05 音声入力の三面変換 ★本システムの入口

本システムで**最も頻繁に実行される**機能であり、職員が毎日・利用者ごとに使う。

**解決する問題**：同じ出来事でも、読む相手によって適切な書き方は違う。しかし職員が3回書き分けるのは現実的ではない。

**入力**：音声入力された生テキスト（句読点なし・口語・専門用語と俗語が混在）

> 「えーっと今日は入浴のとき浴槽またぐの右足あがり悪くて腰支えた あと昼ごはん半分くらい むせこみ一回あり レクは塗り絵で20分くらいで疲れたって言って休んでた」

**出力JSONスキーマ**

```json
{
  "record_text": "入浴時、浴槽をまたぐ際に右足の挙上が不十分であり、腰部を支持して介助を実施。昼食は主食5割程度の摂取。食事中に1回のむせ込みあり。レクリエーション（塗り絵）に参加されたが、約20分で疲労感の訴えがあり休憩された。",
  "family_text": "本日もお元気にお過ごしでした。入浴では手すりを使いながら、職員がお手伝いして湯船に浸かっていただきました。塗り絵では色を丁寧に塗っておられました。お食事の際に一度むせ込みがございましたので、お迎えの際に職員より詳しくご説明させていただきます。",
  "handover_note": "食事中にむせ込み1回あり。次回の食事時は形態と姿勢を要確認。入浴は腰部支持での介助を継続。",
  "requires_verbal_contact": [
    {
      "topic": "食事中のむせ込み",
      "why": "頻度や食形態との関係によって意味が変わる事項であり、ご家族が状況を質問できる形で伝える必要があるため",
      "urgency": "same_day"
    }
  ],
  "family_excluded": [],
  "uncertain": [
    "「昼ごはん半分くらい」から主食5割と判断しましたが、副菜の摂取量は言及がないため補完していません"
  ],
  "detected_items": {
    "meal_staple_rate": 50,
    "meal_side_rate": null,
    "water_ml": null,
    "bathing_performed": true,
    "incident_suspected": true
  }
}
```

**設計上のポイント**

- **1回のAPI呼び出しで3文体を生成する。** 3回に分けると同じ入力トークンを3回支払うことになる。コスト設計上の判断であり、プロンプトキャッシュとの相性も良い（システムプロンプトのキャッシュが1回で済む）
- **`requires_verbal_contact` — 文書に書いたうえで、口頭連絡を確実に実行させる。** 本項目は設計レビューを経て方針を変更した（下の「設計判断の変更履歴」参照）。ご本人の身体状況に関する事実は**必ず家族向け文書にも記載する**。そのうえで、口頭での補足が必要な事項にはこのフラグを立て、送迎担当者のタスクとして表示し、連絡完了を記録する。未完了のまま日をまたいだ場合は管理者へ通知する
- **`family_excluded` — 外すのは3種類だけ。** ①他のご利用者に関する情報（他人の個人情報であり記載できない）②未確定の推測（「虐待の疑い」等。確証なく家族に伝えることは重大な問題であり、別途、市町村への通報という制度上のルートがある）③診断に類する記述（「認知症が進行しているように見える」等は医師の領域）。**それ以外は外さない**
- **`uncertain` — 推測で補完しなかった箇所を明示する。** 記録の捏造を防ぐ。「水分は言及がないので空欄にした」と言わせることが、勝手に数値を埋められるより遥かに安全
- **`detected_items` — 非構造テキストから構造化データを抽出する。** 「昼ごはん半分」から主食5割のトグルが自動選択され、`incident_suspected` が真ならヒヤリハット報告への導線が表示される。職員のタップ数を減らす直接的な効果がある
- **生テキストは必ず原文のまま保存する。** 整形結果は別カラムに持ち、いつでも原文と突き合わせられるようにする。AIが何を変えたかを後から検証できない記録は、法定文書として使えない

**他機能との関係**

```
F-LLM-05（日次・音声入力の三面変換）
   ├─ record_text    → サービス提供記録に保存 → F-LLM-01 / F-LLM-02 の入力ソース
   ├─ family_text    → 日次の連絡帳 → F-LLM-04（月次の家族向け報告）の入力ソース
   └─ handover_note  → F-LLM-03（申し送り）の入力ソース
```

F-LLM-04 の月次報告は、生の記録ではなく**日次の `family_text` を集約して**生成する。既に家族向けに整形済みのテキストを入力にするため、トークン量が減り、文体の一貫性も保たれる。

**設計判断の変更履歴（v1.1 → v1.2）**

当初、「むせ込み」のようにご家族が不安を感じうる事項は家族向け文書から除外し、口頭で伝える設計としていた。文書だけで済ませて職員が口頭連絡を省略することを防ぐ意図だった。

しかしレビューにより、**この設計では口頭連絡が漏れたときにご家族へ何も伝わらない**という欠陥が明らかになった。書きもせず、言いもしないという最悪の結果を許してしまい、さらに伝達の証跡が残らないため「聞いていない」と言われた際に何も示せない。加えて、介護保険制度上、事故・ヒヤリハットにはご家族への報告義務がある。

**変更後**：ご本人の身体状況に関する事実は必ず文書に記載する。ただし文脈なしの単語が独り歩きしないよう、「お迎えの際に詳しくご説明します」という説明の約束とセットで記載し、口頭連絡の実行をシステムで追跡する（F-20）。

> 「むせ込み1回」という記述が何を意味するかは、頻度・食形態・姿勢・その日の体調との関係で全く変わる。ご家族は連絡帳を帰宅後に読むため、その場で質問できる相手がいない。**だから口頭が必要**なのであって、**だから書かない**のではない。ここを取り違えていた。

### 7.4 エラーハンドリング設計

外部API連携における失敗パターンを網羅的に定義する。

| # | 事象 | 検出方法 | 対応 | ユーザーへの表示 |
|---|---|---|---|---|
| 1 | 接続タイムアウト | クライアントタイムアウト（60秒） | 指数バックオフで最大2回リトライ | 「時間がかかっています」→失敗時「再実行」ボタン |
| 2 | レート制限 | HTTP 429 / `rate_limit_error` | `Retry-After` を優先。無ければ指数バックオフ（1s→2s→4s）＋ジッター | 「混み合っています。自動で再試行します」 |
| 3 | サーバ過負荷 | HTTP 529 / `overloaded_error` | 同上 | 同上 |
| 4 | サーバエラー | HTTP 5xx | 指数バックオフで最大2回リトライ | 同上 |
| 5 | 認証エラー | HTTP 401 | **リトライしない**。ログに記録し管理者へ通知 | 「システム設定に問題があります。管理者にご連絡ください」 |
| 6 | リクエスト不正 | HTTP 400 | **リトライしない**。入力長超過の場合は期間を分割して再構成 | 「対象期間が長すぎます。期間を短くしてください」 |
| 7 | 出力のトークン切れ | `stop_reason == "max_tokens"` | `maxTokens` を引き上げて1回だけ再実行 | （自動処理、ユーザーには非表示） |
| 8 | 応答の拒否 | `stop_reason == "refusal"` | リトライしない。ログに記録 | 「この内容は生成できませんでした」 |
| 9 | **JSONパース失敗** | `json_decode` が失敗 | 修正指示を添えて1回だけ再実行 | （自動処理） |
| 10 | **JSONスキーマ不一致** | バリデータで検証失敗 | 不足項目を指摘して1回だけ再実行 → 失敗時は中止 | 「うまく生成できませんでした。手動で入力してください」 |
| 11 | 月次コスト上限超過 | 実行前チェック | **実行しない** | 「今月のAI利用上限に達しました」 |
| 12 | APIキー未設定 | 起動時／実行前チェック | `FakeClient` にフォールバック | 「デモモードで動作しています」バッジを表示 |

**設計上のポイント**

- **リトライすべき失敗と、すべきでない失敗を明確に分ける。** 認証エラーやリクエスト不正をリトライしても成功する可能性はなく、コストとレイテンシを浪費するだけである
- **#9/#10 の「構造化出力の検証失敗」を独立した失敗パターンとして扱う。** これはHTTPレベルでは成功（200）として返るため、通常のHTTPエラーハンドリングでは捕捉できない。LLM連携特有の失敗であり、ここを設計していないシステムは本番で壊れる
- **再実行は1回限りとする。** 無限リトライはコスト暴走に直結する

### 7.5 非同期ジョブ管理（F-LLM-06）

```
[ユーザー] 実行ボタン
     ↓
[Controller] llm_jobs に queued で登録 → job_id を返す（即時レスポンス）
     ↓
[Queue Worker] ジョブ実行（running）
     ↓
[完了] succeeded / failed に更新、結果を保存
     ↓
[Frontend] job_id をポーリングして進捗表示 → 完了時に結果を描画
```

- `llm_jobs` テーブルでステータス（`queued / running / succeeded / failed`）と結果、エラー内容を管理する
- 失敗したジョブは管理画面から**再実行できる**
- 同一対象・同一期間に対する重複実行を防ぐ（実行中の同一ジョブがある場合は新規登録を拒否）

### 7.6 コスト管理（F-LLM-07）

**記録項目**（`llm_requests` テーブル）

| カラム | 内容 |
|---|---|
| `feature` | どの機能からの呼び出しか（F-LLM-01〜05） |
| `model` | 使用モデル |
| `input_tokens` / `output_tokens` | トークン数（APIレスポンスの `usage` から取得） |
| `cache_read_input_tokens` | プロンプトキャッシュのヒット量 |
| `latency_ms` | 応答時間 |
| `status` | `success / failed` |
| `error_type` | エラー種別 |
| `retry_count` | リトライ回数 |
| `estimated_cost_usd` | 推定コスト |

**制御**

- `.env` に月次コスト上限（`LLM_MONTHLY_BUDGET_USD`）を設定し、超過時は実行を拒否する
- 管理画面で機能別・日別のトークン消費とコストを集計表示する
- **プロンプトキャッシュ**を使用し、固定部分（システムプロンプト・介護ドメインの用語定義・出力スキーマ定義）をキャッシュする。`cache_read_input_tokens` を記録することでキャッシュが実際に効いているかを検証可能にする

**コスト試算**（Claude Opus 5：入力 $5.00 / 1M tokens、出力 $25.00 / 1M tokens）

| 機能 | 入力 | 出力 | 1回あたり概算 |
|---|---|---|---|
| F-LLM-01 目標進捗要約 | 約4,000 tokens | 約1,500 tokens | 約 $0.058（約9円） |
| F-LLM-02 リスク抽出 | 約4,000 tokens | 約1,200 tokens | 約 $0.050（約8円） |

利用者20名に対し月1回ずつ実行した場合、月額およそ **$2.2（約340円）**。プロンプトキャッシュ適用でさらに低減する。個人開発の範囲で十分に運用可能な水準である。

### 7.8 音声入力の技術選定

F-LLM-05 の入口となる音声入力について、3方式を比較した。

| # | 方式 | 仕組み | 音声データの行き先 | 実装コスト | 判定 |
|---|---|---|---|---|---|
| ① | **iOS標準キーボードの音声入力** | `<textarea>` にフォーカスし、キーボードのマイクボタンで入力 | Apple（OSの責任範囲） | **ゼロ** | **◎ 採用** |
| ② | Web Speech API（`webkitSpeechRecognition`） | ブラウザのAPIで音声認識 | ブラウザベンダー | 小 | △ 対応ブラウザのみ補助的に |
| ③ | 録音してサーバーで文字起こし | `MediaRecorder` で録音 → 自社サーバー → 文字起こしAPI | **自社サーバー＋外部API** | 大 | **✕ 不採用** |

**① を採用する理由**

- iOS Safari における Web Speech API は、連続認識が途中で停止する、バックグラウンドで動作しない、権限の挙動が不安定といった制約があり、現場で使う機能として信頼できない
- OSの標準機能であるため、**職員が既に使い慣れている**（LINEやメールで日常的に使っている操作と同じ）
- 追加の実装もライブラリも不要で、**アプリが受け取るのは文字列だけ**になる

**③ を不採用にする理由（設計上の主張）**

音声そのものが要配慮個人情報である。③を採ると、保護すべき対象が「テキスト」から「音声ファイル」へ広がり、自社サーバーでの保管・暗号化・削除、外部文字起こしAPIへの送信という新たなリスクが発生する。加えて文字起こしのAPI利用料も追加で発生する。

**得られる精度の向上に対して、保護責任とコストの増加が見合わない。** したがって不採用とする。

**① を前提としたときに必要になる設計**

音声入力されたテキストには、次の特徴がある。

- 句読点が入らない
- 口語表現になる（「〜って言ってた」「〜な感じ」）
- 専門用語が誤変換される（「褥瘡」→「じょくそう」「食奏」等）
- 言い直し・フィラーが混ざる（「えーっと」「あの」）

つまり、**音声入力をそのまま記録として保存することはできない**。F-LLM-05 による整形が前提としてセットになる。音声入力とAI整形は、片方だけでは成立しない一体の機能である。

**②の扱い**：`window.SpeechRecognition` が利用可能なブラウザ（Android Chrome・デスクトップChrome等）では、アプリ内マイクボタンによる連続入力を補助的に提供する。利用できない環境ではボタンを表示しない（プログレッシブ・エンハンスメント）。

## 9. データモデル

### 9.1 主要エンティティ

```
facilities ──< residents ──< care_plans ──< care_plan_goals
                   │
                   ├──< service_records ──< vital_signs
                   │         │            ├─< meal_records
                   │         │            ├─< bathing_records
                   │         │            └─< training_records
                   │         │
                   │         └──< (LLM入力ソース)
                   │
                   ├──< weight_records
                   ├──< incident_reports
                   ├──< family_reports
                   └──< risk_assessments ──< risk_findings

care_levels (マスタ) ──< residents
users ──< service_records (記録者)
llm_jobs ──< llm_requests
```

#### `service_records` の記録テキスト関連カラム

音声入力とAI整形の関係上、1つの記録に対して4種類のテキストを保持する。

| カラム | 内容 | 由来 |
|---|---|---|
| `raw_note` | 音声入力された生テキスト（原文のまま・未加工） | 職員 |
| `record_text` | 記録用に整形されたテキスト（法定文書の本体） | F-LLM-05 → 職員が確認・修正 |
| `family_text` | 家族向けに整形されたテキスト | F-LLM-05 → 職員が確認・修正 |
| `handover_note` | 申し送り用メモ | F-LLM-05 → 職員が確認・修正 |
| `record_text_edited_by_human` | 職員が整形結果を修正したか（真偽値） | システム |

**`raw_note` を必ず残す理由**：AIが何を変えたのかを後から検証できない記録は、法定文書として使えない。原文と整形結果を突き合わせられることが、記録の信頼性を担保する。また、整形結果に誤りが見つかったときの原因追跡（プロンプトの問題か、そもそも入力が曖昧だったのか）にも必要である。

### 9.2 正規化方針

求人要件に「DBの正規化（第1〜第3正規形）への理解」が挙げられているため、**正規化の根拠を設計書に明記する**方針とする。

#### 第1正規形：繰り返し項目の排除

| 非正規な設計 | 本システムの設計 | 根拠 |
|---|---|---|
| `care_plans` に `goal_1`, `goal_2`, `goal_3` カラムを持つ | `care_plan_goals` テーブルへ分離（1対多） | 短期目標の件数は可変。カラム固定では4件目に対応できず、目標単位の進捗評価（F-LLM-01）もできない |
| `service_records` にバイタルを1組だけ持つ | `vital_signs` テーブルへ分離 | 来所時・入浴前後など1日に複数回測定するため |

#### 第2正規形：部分関数従属の排除

`meal_records` は「サービス提供記録 × 食事区分（昼食／おやつ）」で一意になる。複合主キー `(service_record_id, meal_type)` を採用すると、`service_date` のような `service_record_id` のみに従属する項目を持たせた際に部分関数従属が発生する。

→ **サロゲートキー `id` を主キーとし、`(service_record_id, meal_type)` にユニーク制約を課す**。日付等は `service_records` 側にのみ保持し、重複を持たせない。

#### 第3正規形：推移的関数従属の排除

| 非正規な設計 | 本システムの設計 | 根拠 |
|---|---|---|
| `residents` に `care_level_code` と `care_level_name`（「要介護3」）を両方持つ | `care_levels` マスタへ分離し、`residents.care_level_id` で参照 | `care_level_name` は `care_level_code` に従属しており、`residents` の主キーには推移的にしか従属しない。名称変更時の更新漏れ（更新不整合）を防ぐ |
| `service_records` に `staff_name` を持つ | `users.id` を参照 | 同上。職員の改姓時に過去記録すべての更新が必要になる |

#### あえて正規化しない箇所（非正規化の判断）

| 項目 | 判断 | 理由 |
|---|---|---|
| `llm_requests.estimated_cost_usd` | 保存する（計算可能だが冗長に持つ） | 料金体系はモデルごとに変わり将来改定もあるため、**実行時点の単価で計算した結果**を記録することに意味がある。導出可能だが再現不可能な値 |
| `risk_findings.evidence`（JSON型） | JSON型で保存 | LLMが返す根拠配列は件数・構造が可変で、リレーショナルに展開しても検索要件がない |

**この節の意図**：正規化は「ルールだから従う」ものではなく、**更新不整合を防ぐための判断**であり、要件によっては意図的に崩す判断もあり得る、ということを設計書として示す。

### 9.3 データ保護設計

#### 9.3.1 前提：DB設計で流出は防げない

本システムは要配慮個人情報（健康状態・病歴）を扱う。ここで設計の前提を明確にしておく。

> **データベース設計は、情報流出を「防ぐ」ものではない。流出を防ぐのはネットワーク境界・認証・認可・脆弱性対策である。**
> **データベース設計が担うのは、防御が突破されたときに「被害を最小化する」ことである。**

この区別を曖昧にしたまま「暗号化しているので安全です」と説明する設計書は実務でしばしば見かけるが、正しくない。本節の施策はすべて**多層防御の最終層**として位置づける。

#### 9.3.2 施策

| # | 施策 | 対象 | 実装方針 | 効果 |
|---|---|---|---|---|
| 1 | **データ最小化** | 全体 | マイナンバー・金融情報は保持しない。既往歴はケアに必要な範囲に限定する | **持っていない情報は漏れない。** 最も効果が高く、コストがゼロ |
| 2 | **カラムレベル暗号化** | 被保険者番号、住所、電話番号、家族連絡先 | Laravel の `encrypted` キャスト（AES-256, `APP_KEY` で復号） | DBダンプが流出しても鍵がなければ復号できない |
| 3 | **Blind Index** | 氏名カナ（検索が必要なため暗号化できない） | `name_kana_hash = HMAC-SHA256(正規化カナ, 専用キー)` を別カラムに保持し、完全一致検索に使う | 平文を持たずに検索を成立させる |
| 4 | **氏名を複製しない** | 記録系の全テーブル | `resident_id` のみを保持し、氏名は `residents` にのみ置く | 個人情報の保管箇所を1テーブルに集約する。第3正規形の方針と一致 |
| 5 | **アクセスログ（F-19）** | 全参照操作 | `access_logs`：`user_id` / `resident_id` / 操作種別 / IP / 日時 | **流出時に「誰の情報が見られたか」を特定できる。** 内部不正の抑止にもなる |
| 6 | **保存期間管理と物理削除** | 記録系 | 法定保存期間の経過後、バッチで物理削除する | 保持し続けないことでリスク総量を減らす |
| 7 | **DBユーザーの権限分離** | 運用 | アプリ用ユーザーに DDL 権限を与えない。バックアップ用は `SELECT` のみ | SQLインジェクション成功時の被害範囲を限定する |
| 8 | **本番データを開発環境に持ち込まない** | 運用 | Seeder は架空データのみ。マスキングダンプの手順をREADMEに明記 | 実務で最も多い流出経路の一つを塞ぐ |
| 9 | **LLM監査ログはマスク後のみ保存** | `llm_requests` | 7.2節の方針どおり | ログ経由での個人情報の二次流出を防ぐ |

#### 9.3.3 トレードオフと限界（隠さず明記する）

施策には副作用と限界がある。設計書としてこれを書かないことは不誠実であると考え、明記する。

| 施策 | 限界・副作用 |
|---|---|
| カラムレベル暗号化 | **暗号化したカラムは `WHERE` / `ORDER BY` / インデックスが使えない。** 検索要件のある項目には適用できない。全カラムを暗号化すると運用が破綻するため、**リスクベースで対象を絞る** |
| Blind Index | **頻度分析に弱い。** 氏名カナのようにエントロピーが低い値は、ハッシュ化しても出現頻度から推測されうる。完全な対策ではなく、平文保存よりましという位置づけである |
| `APP_KEY` による暗号化 | **鍵がアプリケーションサーバー上に存在する以上、サーバー自体が侵害されれば復号される。** 本システムは個人開発のため環境変数での管理に留めるが、**実運用では AWS KMS 等の鍵管理サービスでデータと鍵を分離する必要がある** |
| 物理削除 | 誤削除が復旧できない。削除対象の抽出条件を慎重に設計し、削除前に件数ログを残す |
| アクセスログ | ログ自体が個人情報の所在を示す。ログにも保存期間とアクセス制限を設ける |

#### 9.3.4 公開リポジトリで気を付けること

本システムはGitHubで公開するため、以下を手順として固定する。

1. **`.env` を絶対にコミットしない。** `APP_KEY` と Claude APIキーが含まれる。`.gitignore` を最初に確認する
2. **公開前に全コミット履歴を検査する。** 一度でもコミットした秘密情報は、後のコミットで削除しても履歴に残る
3. **デモデータはすべて架空であることをREADMEに明記する。** 実在の事業所名・利用者名・住所は一切使用しない
4. **`.env.example` にはダミー値のみを置く**
